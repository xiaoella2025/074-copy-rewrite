# 074 对标批量后台执行与中断恢复

日期：2026-10-17。状态：设计已获用户确认；实施计划待确认，尚未修改产品代码或正式数据。

## 目标与现状

用户已要求继续补齐 Story 差异，并要求每完成一项说明实现方式。此次先处理清单 07 中的批量执行与恢复，完成后继续同组其他缺口。

`assets/benchmark_batch.js` 目前在页面内顺序调用提取、导出、标记、带货判定接口；`running/done/stopped` 仅在内存。关闭页面后循环结束；刷新也无法恢复完整批次。现有带货 SQLite 回执已能避免未确认请求重复收费，继续复用。

只读诊断另用独立临时目录重现了并发问题：识别执行期间新增的手动文案会被识别结束后的旧结果覆盖。此验证未调用真实 ASR、未修改正式数据，因此保存前快照校验列入本项必要修复。

验收目标：

- 操作仍从原有作品列表批量按钮发起，保持紧凑布局。
- 切换页面、刷新或关闭页面，后端仍继续这一批。
- 页面重新打开能看到原批次与真实进度、每条成功/失败原因。
- 软件退出或崩溃后显示中断；用户点击继续后，只补尚未完成项。
- 成功项不重做，结果未确认的收费判定不自动重发。

## 方案选择

采用独立的对标后台作业记录，复用已有选品后台作业的模式、`task_queue.atomic_json` 原子写入和既有对标处理函数。

另一个可行方案是扩展视频制作总队列，加入对标任务类型；但这会影响现有视频串行顺序、历史任务类型和批次统计。此次保持视频队列接口和规则不变。

## 后端与数据

- 新建 `benchmark_batch_jobs.py`，批次记录放在 074 自己的数据目录 `benchmark/batch-jobs/`。
- 每条记录保存批次 ID、操作类型、按选择顺序排列的账号/作品稳定 ID、标记目标值、创建/更新时间，以及每条的状态、错误和导出产物引用。带货判定还保存提交时的文本/标题指纹。
- 不保存 API Key；不复制整篇文案作为批次配置；昵称和标题不参与身份判断。
- 创建批次时先验证全部身份与操作，再原子落盘，随后启动后端线程。前端生成请求 ID，重复点击或响应丢失后的同 ID、同内容重交只返回原批次；同 ID 携带不同内容时拒绝。
- 同一数据目录同一时间执行一个对标批次；存在活动批次时，新批次请求返回冲突并提示查看当前进度，不把另一批作品当成已提交。
- 状态为 `queued/running/stopping/interrupted/completed/stopped`；每条为 `pending/running/succeeded/failed/unconfirmed`。
- 导入对标业务备份不导入或清除这些执行记录、带货请求回执，不触发作业。

## 执行与恢复

- 提取：复用已有本地 ASR 与原视频下载；执行前再次检查是否已有文案，已有则直接复用。识别期间如果用户新增或改动文案，保存前校验快照，保留用户的新稿件。
- 导出：复用既有文案导出函数，已完成的产物保留；桌面完成后可打开现有导出位置，网页通过产物链接下载。
- 标记：固定本次用户选择的目标值，不因刷新后状态变化而反向切换；保留作品其他字段。
- 带货：仍调用现有带货判定与持久回执。完成回执可复用；未确认回执保持未确认，不能通过“继续批次”绕过防重复限制。若文案/标题指纹已变化，旧批次拒绝为变化后的内容发新请求，提示重新选择提交。
- 点击停止后不再领取下一条；当前已提交的操作等待返回并保存结果。停止不删除已完成文案、标记或导出文件。
- 软件重启后不自动启动旧作业。重开页面识别中断记录，点击“继续未完成项”才恢复；成功项跳过。收费状态未知的项单独展示，其他已获用户明确继续指令的待处理项仍可继续。
- 网络读取状态失败只显示连接提示，不据此宣称后台停止或重交整批。
- 模型选择沿用现有对标操作规则：执行时使用当前文案模型；恢复不主动切换模型、不重复已完成的模型请求。此次开发验收不调用真实付费模型。

## 页面与接口

新增经过现有桌面 cookie/Origin 校验的批次列表/状态、创建、停止、继续接口。

前端原有 `create/render/pick/run/stop` 接口保持可用，执行改为提交后端作业并读取状态。利用页面已有轮询刷新，不新增常驻遮罩或大面积面板。

原工具栏显示“提取/导出/标记/判定带货：已完成 n/N”，分别列成功、失败、待确认数量；中断时显示继续入口。恢复记录按已存稳定 ID 定位，不重新扩大到当前筛选出的全部作品。
